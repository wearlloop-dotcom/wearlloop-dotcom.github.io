## 1. ปัญหาที่ระบบนี้แก้

AI ผู้ช่วย (LLM) มีข้อจำกัด 3 อย่างที่ทำให้ "เก่งแต่ลืม":

1. **Context จำกัด** — ยัดข้อมูลเข้าไปได้จำนวนหนึ่งต่อครั้ง ถ้าเอกสารใหญ่มากก็ยัดไม่หมด
2. **ไม่จำข้ามเซสชัน** — ปิดแชทแล้วเริ่มใหม่ ต้องเล่าบริบทซ้ำ
3. **ยิ่งยัดเยอะยิ่งแพง/ช้า/มั่ว** — token ที่ใช้ = ต้นทุนจริง และข้อมูลเยอะเกินทำให้ตอบเบลอ

**อาการที่บอกว่าถึงเวลาต้องมีระบบนี้:**
- ไฟล์เอกสารในโปรเจคเริ่มใหญ่ (หลักหมื่น–แสนบรรทัด) จน AI อ่านทั้งก้อนไม่ไหว/แพง
- ต้องเล่าบริบทเดิมซ้ำ ๆ ทุกครั้งที่เปิดงานใหม่
- ความรู้/การตัดสินใจเก่ากระจัดกระจาย หาไม่เจอ ทำผิดซ้ำ
- อยากให้ AI "ตัดสินใจโดยอิงข้อมูลจริงของธุรกิจ" ไม่ใช่เดาจากความรู้ทั่วไป

> **ข้อสังเกตสำคัญจาก community:** "จุดสำคัญไม่ใช่มีโน้ตเยอะ แต่ต้องทำให้ข้อมูล *เชื่อมกัน*
> และ *ถูกเรียกกลับมาใช้ได้ตอนต้องตัดสินใจ*" และ "AI ฉลาดแค่ไหน อยู่ที่สิ่งที่เรายัดเข้าไป
> ตอนคุย (input) ไม่ใช่ปริมาณไฟล์ที่มี" → ระบบนี้จึงเน้น **retrieval ที่ตรง** มากกว่าคลังใหญ่

## 2. แนวคิดหลัก: LLM wiki คืออะไร (ต่างจาก RAG ยังไง)

**RAG แบบเดิม** = ตอนถาม ค่อยไปค้นเอกสารดิบ ตัดเป็นชิ้น ๆ มายัดให้ LLM ทุกครั้ง →
ทำงานซ้ำทุก query, คุณภาพขึ้นกับการตัดชิ้น, ไม่มีการ "เข้าใจสะสม"

**LLM wiki (แนวที่ใช้ใน memo นี้)** = LLM **ค่อย ๆ สร้างและดูแล "วิกิ" ของตัวเอง** เป็น
markdown ที่สรุป/เชื่อมโยงความรู้ไว้ล่วงหน้า พอมีข้อมูลใหม่เข้ามา LLM ไม่ได้แค่เก็บดิบ ๆ แต่
**อ่าน → กลั่นสาระ → ไปแก้หน้าที่เกี่ยวข้อง → จดว่าอะไรขัดกัน** → วิกิเป็น "สินทรัพย์ที่โตขึ้น
เรื่อย ๆ" (persistent, compounding artifact) ความรู้ถูกเรียบเรียง *ครั้งเดียว* แล้วรักษาให้สดใหม่
ไม่ต้อง re-derive ทุกครั้งที่ถาม

**ข้อดีที่ตามมา:**
- ประหยัด token — เพราะอ่านสารบัญแล้ว route ไปเฉพาะหน้าที่เกี่ยว ไม่ scan ทั้งคลัง
- scale ได้ — คลังโตเป็นร้อย ๆ หน้าก็ไม่พัง เพราะไม่เคยโหลดทั้งหมดพร้อมกัน
- ตรวจสอบได้ — เป็น markdown ใน git, history = audit trail
- ไม่ lock vendor — ย้ายไป AI เจ้าอื่นได้ เพราะเป็นไฟล์ธรรมดา

## 3. สถาปัตยกรรม 3 ชั้น (ละเอียด)

```
┌─────────────────────────────────────────────────────────────┐
│ ชั้น 1: RAW SOURCES  (มนุษย์คัด, AI อ่านได้ห้ามแก้)            │
│   เอกสารต้นฉบับ: audit, สเปค, บทความ, โน้ตประชุม, ข้อมูลดิบ     │
│   → เปรียบเหมือน "หนังสือต้นฉบับในห้องสมุด"                     │
├─────────────────────────────────────────────────────────────┤
│ ชั้น 2: THE WIKI  (AI เป็นเจ้าของ ดูแลเองทั้งหมด)             │
│   index.md   = สารบัญ (routing) — อ่านก่อนเสมอ                 │
│   log.md     = บันทึกเหตุการณ์ (append-only)                   │
│   <domain>.md = หน้าที่กลั่นแล้ว (Insight/Decision/Next-action) │
│   → เปรียบเหมือน "บัตรรายการ + สมุดสรุปที่บรรณารักษ์เขียน"       │
├─────────────────────────────────────────────────────────────┤
│ ชั้น 3: SCHEMA  (ไฟล์กติกา — สำคัญที่สุด)                      │
│   CLAUDE.md / AGENTS.md: page มีกี่ชนิด, ตั้งชื่อยังไง,         │
│   เมื่อไหร่สร้างหน้าใหม่ vs แก้หน้าเดิม, ขั้นตอน ingest/query/lint │
│   → เปรียบเหมือน "คู่มือบรรณารักษ์" ที่เปลี่ยน AI ทั่วไป         │
│     ให้เป็นบรรณารักษ์ที่มีวินัย                                 │
└─────────────────────────────────────────────────────────────┘
```

**หัวใจของทั้งระบบ (กฎเหล็ก):**
> AI **อ่าน `index.md` ก่อนเสมอ** เพื่อหาว่าเรื่องนี้อยู่หน้าไหน แล้วค่อยเปิดเฉพาะหน้านั้น
> — **ห้ามโหลดไฟล์ดิบขนาดใหญ่ทั้งก้อน** นี่คือสิ่งที่ทำให้ประหยัด token และ scale ได้

**ทำไม Schema ถึงสำคัญที่สุด:** ถ้าไม่มีกติกา AI จะสร้างหน้าซ้ำ ๆ ตั้งชื่อมั่ว ลืมอัปเดต
cross-reference → คลังรก. Schema ที่ดี = "มีทางเดียวที่ชัดต่อ 1 การกระทำ" (one obvious path)
พอระบุ page types ครบ AI จะทำถูกราว ~90%

## 4. โครงไฟล์ + เทมเพลตทุกไฟล์

```
docs/wiki/
├── index.md          ← สารบัญ อ่านก่อนเสมอ
├── log.md            ← บันทึกเหตุการณ์ append-only
├── <domain-a>.md     ← หน้า distilled
├── <domain-b>.md
└── ...
CLAUDE.md / AGENTS.md ← เพิ่มหัวข้อ "Wiki schema"
```

### 4.1 `index.md` (สารบัญ / routing)
```markdown
# Wiki Index — ⚠️ อ่านหน้านี้ก่อนเสมอ แล้วเปิดเฉพาะหน้าที่เกี่ยว

_อัปเดตทุกครั้งที่ ingest • 1 บรรทัด/หน้า • จัดกลุ่มตาม PARA_

## Projects (งานมีเป้า/เดดไลน์)
- [checkout-flow](checkout-flow.md) — ปัญหา+ทางแก้ flow ชำระเงิน (สถานะ: กำลังทำ)

## Areas (ความรับผิดชอบต่อเนื่อง)
- [stock](stock.md) — กติกา/บทเรียนการจัดสต็อก
- [customer-journey](customer-journey.md) — จุดที่ลูกค้าหลุด + วิธีแก้

## Resources (ความรู้อ้างอิง)
- [brand-voice](brand-voice.md) — โทนการเขียน/คำที่ใช้-ห้ามใช้

## Archive (จบแล้ว/เลิกใช้)
- [old-pricing-2025](archive/old-pricing-2025.md) — โครงราคาเก่า (เก็บอ้างอิง)
```

### 4.2 `log.md` (บันทึกเหตุการณ์)
```markdown
# Log — append-only (ห้ามแก้ของเก่า ต่อท้ายอย่างเดียว)

## [2026-07-13] ingest | สรุป audit สต็อก Q2
- สร้าง stock.md, อัปเดต index
- insight: ไซซ์ L โทนเข้มหมุนช้า

## [2026-07-13] decision | เลิกสั่งชุดโทนเข้ามไซซ์ L รอบหน้า
- อ้างอิง: stock.md

## [2026-07-14] lint | ตรวจคลัง เจอ 1 orphan page แก้แล้ว
```
> ทำไมต้อง append-only: ได้ประวัติการตัดสินใจตามเวลา + ใช้ `grep "^## \[" log.md | tail`
> ดูล่าสุดได้เร็ว + เป็น audit trail

### 4.3 หน้า distilled `<domain>.md`
```markdown
# <ชื่อโดเมน>
> raw: [ไฟล์ต้นฉบับที่กลั่นมา](../BIGFILE.md#section) • อัปเดตล่าสุด: 2026-07-13

## Insight (รู้อะไรบ้าง)
- ข้อเท็จจริง/รูปแบบที่ค้นพบ (พร้อมเลข/หลักฐานถ้ามี)

## Decision (ตัดสินใจอะไรไปแล้ว + เพราะอะไร)
- ...

## Next action (ต้องทำอะไรต่อ)
- [ ] ...

## Links (หน้าที่เกี่ยวข้อง)
- [[stock]] [[forecast]]
```
> กฎ: **หน้า distilled ต้องสั้น** (สรุป ไม่ใช่ก็อปดิบมาวาง) — รายละเอียดเต็มอยู่ที่ raw แล้ว

## 5. Schema — บล็อกที่ต้องเขียนใน CLAUDE.md / AGENTS.md

ก็อปไปวางในไฟล์ instruction ของโปรเจคใหม่ แล้วปรับชื่อ path ให้ตรง:

```markdown
## Wiki / Second Brain (กติกาการใช้คลังความรู้)

**Retrieval rule (สำคัญสุด):**
- ก่อนตอบคำถามที่ต้องใช้บริบทโปรเจค → อ่าน `docs/wiki/index.md` ก่อนเสมอ
- เปิดเฉพาะหน้าที่ index ชี้ว่าเกี่ยว **ห้าม** อ่านไฟล์ดิบขนาดใหญ่ทั้งก้อน
- ถ้า index ไม่มีหัวข้อที่ตรง → บอกผู้ใช้ + เสนอสร้างหน้าใหม่

**Page types:**
- `index.md` = สารบัญ (1 บรรทัด/หน้า, จัดตาม PARA)
- `log.md` = บันทึก append-only
- `<domain>.md` = หน้า distilled (Insight/Decision/Next-action)

**Ingest (รับข้อมูลใหม่):**
1. อ่าน source → กลั่นสาระ
2. เขียน/แก้หน้า distilled ที่เกี่ยว
3. อัปเดต index 1 บรรทัด
4. ต่อท้าย log 1 entry
5. หน้าเดียวอาจกระทบ 5-15 หน้า — อัปเดต cross-reference ให้ครบ

**เมื่อไหร่สร้างหน้าใหม่ vs แก้หน้าเดิม:**
- หัวข้อใหม่จริง ๆ (ยังไม่มีหน้าไหนครอบ) → สร้างใหม่
- ต่อยอด/แก้ของเดิม → แก้หน้าเดิม (กัน orphan page + ข้อมูลซ้ำ)

**ห้าม:** แก้ไฟล์ raw (อ่านได้อย่างเดียว) • ก็อปดิบมาวางในหน้า distilled • ลืมอัปเดต index/log
```

## 6. PARA — วิธีจัดหมวดใน index

PARA = กรอบจัดข้อมูลตาม "ต้องใช้ตอนไหน" (ไม่ใช่ตามหัวข้อ) — ช่วยให้ AI รู้ว่าเรื่องไหนเกี่ยวกับงานอะไร

| หมวด | คือ | อายุ | ตัวอย่าง |
|---|---|---|---|
| **P**rojects | งานมีเป้า+เดดไลน์ | สั้น จบแล้วย้ายไป Archive | เปิดฟีเจอร์ใหม่, แคมเปญ |
| **A**reas | ความรับผิดชอบต่อเนื่อง | ยาว ไม่จบ | สต็อก, บัญชี, ลูกค้าสัมพันธ์ |
| **R**esources | ความรู้อ้างอิง | ยาว หยิบมาใช้เมื่อต้องการ | brand voice, สเปค, กติกา |
| **A**rchive | จบแล้ว/เลิกใช้ | นิ่ง | โปรเจคปิดแล้ว, ราคาเก่า |

> เคล็ด: พอ Project จบ ให้ย้ายหน้าไป Archive (ยังอ้างอิงได้) — index จะไม่รก

## 7. 4 Workflow หลัก (ละเอียด + ตัวอย่าง)

### 7.1 Capture (เก็บเข้ามา)
เก็บทุกอย่างที่เข้ามา: ไอเดีย, บทความ, โน้ตประชุม, สิ่งที่ต้องทำ — ตอนนี้ยังเป็นของดิบ ยังไม่จัด
> ตัวอย่าง: จบประชุมทีม → ทิ้งโน้ตดิบไว้ที่ `docs/wiki/_inbox/` หรือส่งผ่าน bot

### 7.2 Organize (จัดหมวด)
เอาของที่ capture มาแยกเข้า PARA เพื่อให้ AI รู้ว่าข้อมูลนี้เกี่ยวกับงานอะไร
> ตัวอย่าง: โน้ตประชุมเรื่อง "ลด lead time ซัก" → เข้า Area `laundry`

### 7.3 Distill (กลั่น)
ให้ AI สรุปสาระสำคัญ ดึง **Insight / Decision / Next-action** ออกจากโน้ตดิบ เขียนเป็นหน้า distilled
> ตัวอย่าง input (raw): บันทึกประชุม 3 หน้า พูดถึงชุดที่เช่าออกช้า
> ตัวอย่าง output (distilled) ในหน้า `stock.md`:
> - Insight: ชุดโทนเข้มไซซ์ L หมุน < 1 รอบ/เดือน เพราะลูกค้า 70% ไซซ์ S-M
> - Decision: รอบสั่งหน้า ลดโทนเข้มไซซ์ L 50%
> - Next action: [ ] ทำ report เช็คซ้ำอีก 1 เดือน

### 7.4 Retrieve & Execute (ดึงมาใช้ตอนทำงาน)
ก่อนเริ่มงาน AI อ่าน index → route ไปหน้าที่เกี่ยว → สรุปบริบท → เสนอสิ่งที่ควรทำต่อ
> ตัวอย่าง: ผู้ใช้ถาม "รอบนี้ควรสั่งชุดอะไร" → AI เปิด index เห็น `stock.md` + `forecast.md`
> → อ่าน 2 หน้านั้น → ตอบพร้อมเหตุผลอิงข้อมูลจริง (ไม่ต้องอ่าน audit ดิบ 100 หน้า)

## 8. Automation

### 8.1 Skill `/ingest <ไฟล์|ลิงก์|โน้ต>`
ทำ Distill อัตโนมัติ: อ่าน source → เขียน/แก้หน้า wiki → อัปเดต index → ต่อท้าย log
เป็นสเต็ปเดียวจบ ลดโอกาสลืมอัปเดต cross-reference

### 8.2 Skill `/lint`
health-check คลังเป็นระยะ หาปัญหา:
- **contradiction** — 2 หน้าพูดขัดกัน
- **stale claim** — ข้อมูลเก่าที่น่าจะเปลี่ยนแล้ว
- **orphan page** — หน้าที่ไม่มีใครลิงก์ถึง / ไม่อยู่ใน index
- **missing cross-ref** — ควรลิงก์กันแต่ไม่ได้ลิงก์
> drift (ข้อมูลเพี้ยนสะสม) คือสาเหตุพังอันดับ 1 → ตั้ง lint เป็นรอบ (เช่น ทุกสัปดาห์)

### 8.3 Capture อัตโนมัติ (ออปชัน)
bot (เช่น Telegram) รับข้อความ/รูป → คัดแยกด้วย hashtag ลง vault/project อัตโนมัติ →
เวลาดึงมาวิเคราะห์ agent อ่าน readme guide เพื่อรู้ว่า hashtag/keyword ไหนไปไฟล์ไหน

## 9. Multi-Agent — ทีมผู้ช่วย (ละเอียด)

เสริมฝั่ง "ลงมือทำ" — แตกงานใหญ่/ซ้ำ ให้ AI หลายตัวช่วยกันแบบมีโครง

### 9.1 รูปแบบ (จากภาพ terminal ของ community)
```
หัวหน้า (โมเดลตัวเก่งสุด) รับงาน
  │
  ├─ ประเมิน: งานซับซ้อนไหม?
  │     ├─ ซับซ้อน → เรียก "สถาปนิก" วางแบบ/architecture ก่อน
  │     └─ ง่าย    → ทำเอง
  │
  ├─ แตกงาน → เรียก "ลูกทีม" หลายตัวทำ *ขนาน* (fast-worker)
  │     เช่น "Dispatching 5 parallel builders for 7 pages"
  │
  ├─ ทดสอบ → โมเดลเล็ก/เร็ว รัน ~100 cases หา error
  │
  └─ ตรวจ → reviewer (เช่น code-review / โมเดลอื่น) → เจอผิดแก้เอง
```

### 9.2 map เข้าเครื่องมือจริง (กรณี Claude Code)
| บทบาทในทีม | เครื่องมือจริง |
|---|---|
| หัวหน้าประเมิน scope | main loop (โมเดลหลัก เช่น Opus) |
| สถาปนิกวางแบบ | subagent `Plan` หรือ model `fable` ผ่าน Agent tool |
| ลูกทีมรุมทำขนาน | `Agent` หลายตัว หรือ `Workflow` (parallel/pipeline) |
| ทดสอบจำนวนมาก | agent + โมเดลเล็ก (เช่น haiku) เป็น model override |
| ตรวจงาน / ซ่อม | `/code-review`, `/verify`, adversarial-verify ใน Workflow |

### 9.3 ใช้กับงานแบบไหน
- งานซ้ำเยอะทีเดียว: "ตรวจทุกหน้า/ทุกไฟล์พร้อมกัน"
- audit เชิงระบบ: ตรวจความถูกต้อง/ความปลอดภัยหลายมุมขนานกัน
- review ก่อน deploy: หลายผู้ตรวจ (bug/perf/security) แล้วรวมผล
- งานสร้างจำนวนมาก: สร้างหลายหน้า/หลายรูปพร้อมกันตามสเปคเดียว

### 9.4 กติกาสำคัญ
- **pipeline by default** — ให้แต่ละชิ้นไหลผ่านทุกสเตจอิสระ ไม่ต้องรอกันเป็นแถว (เร็วกว่า)
- **ยืนยันแบบปรปักษ์ (adversarial verify)** — ให้ผู้ตรวจพยายาม "หักล้าง" ผลลัพธ์ ไม่ใช่แค่เห็นด้วย
- **ทำ multi-agent เมื่องานคุ้ม** เท่านั้น — งานเล็กทำเองเร็วกว่า

## 10. เรื่อง scale, token และทำไม "ไม่ทำ infra หนัก"

**สิ่งที่ community เจอจริง:** ใช้ Obsidian เป็น second brain พอทะลุ ~30k ไฟล์เริ่มตอบไม่ตรง
และ "เปลือง token สุด ๆ" → บางคนเลยไปทำ knowledge graph (Neo4j/graphiti) + oracle (ARRA)

**แต่มีข้อโต้แย้งที่สำคัญ:** ระบบหนักพวกนั้น **เหมาะกับ AI ที่ไม่มี memory ในตัว** เท่านั้น
ถ้า AI มี memory + skill + subagent อยู่แล้ว (เช่น Claude) → **ไม่จำเป็น** แค่:
- ให้มันจัดการ memory index เอง (สั่งให้ค้น → ทำเป็น skill ถ้ายังไม่มี)
- เทคนิคที่ใช้บ่อย → ทำเป็น skill กลาง = ได้ second brain โดยไม่ต้องตั้ง DB

**เกณฑ์ตัดสินใจ:**
| สภาพ | เลือก |
|---|---|
| คลังหลักสิบ–ร้อยหน้า, AI มี memory | **markdown wiki + index/routing** (memo นี้) — พอ |
| คลังหลักหมื่นไฟล์+, ต้อง temporal reasoning | ค่อยพิจารณา hybrid search (SQLite FTS5 + embeddings) |
| ต้อง track ข้อเท็จจริงเปลี่ยนตามเวลาแบบซับซ้อน | ค่อยพิจารณา knowledge graph |

> เริ่มจากเบาที่สุดที่แก้ปัญหาได้ก่อน — อย่า over-engineer ตั้งแต่ยังไม่เจอเพดาน

## 11. ความปลอดภัย + PII + ย้ายค่าย

- **PII (ข้อมูลส่วนบุคคล):** ชื่อ/เบอร์/ที่อยู่/ประวัติลูกค้า **ห้าม** commit ลงไฟล์ wiki ในรีโป
  → เก็บฝั่ง backend/DB ที่มี auth (เช่น Supabase + gateway). wiki เก็บได้แค่ "รูปแบบ/บทเรียน"
  ที่ไม่ระบุตัวบุคคล เช่น "ลูกค้ากลุ่มไซซ์ S-M หมุนไว" (ไม่ใช่รายชื่อ)
- **ความลับ/คีย์:** ห้าม commit API key/secret ลง wiki
- **ย้ายค่าย (vendor lock-in):** เก็บทุกอย่างเป็น **markdown + git** → ย้ายไป AI เจ้าอื่น
  (codex/gemini) ได้ทันที เพราะ second brain เป็นไฟล์ ไม่ผูกกับ tool ใด
- **Obsidian เป็น front-end ได้เลย:** โฟลเดอร์ markdown เปิดเป็น Obsidian vault ดู visual/กราฟ
  ลิงก์ได้ทันที (ไม่ต้องแปลงอะไร)

## 12. Failure modes ที่เจอบ่อย + วิธีกัน

| อาการ | สาเหตุ | วิธีกัน |
|---|---|---|
| AI ยังเปลือง token/ช้า | ไม่ได้บังคับอ่าน index ก่อน | เขียน retrieval rule ให้ชัดใน schema |
| คลังรก หน้าซ้ำ | ไม่มีกติกาสร้าง vs แก้ | ระบุ "เมื่อไหร่สร้างหน้าใหม่" ใน schema |
| ข้อมูลขัดกัน/เก่าค้าง (drift) | ไม่ได้ lint | ตั้ง `/lint` เป็นรอบ |
| orphan page (หน้าลอย) | ลืมอัปเดต index | ให้ ingest อัปเดต index เป็นสเตจบังคับ |
| ตอบมั่วเรื่องตัวเลข/ข้อมูลสำคัญ | ดึงผิดหน้า/ไม่มีหน้า | index ต้องคมพอ + ถ้าไม่มีให้บอก ไม่เดา |
| หน้า distilled บวมเท่าไฟล์ดิบ | ก็อปดิบมาวาง | ย้ำกฎ "สรุป ไม่ใช่ก็อป" |

## 13. ขั้นตอน integrate โปรเจคใหม่ (ทีละสเต็ป)

**สเต็ป 1 — ตั้งโครง**
- สร้างโฟลเดอร์ `docs/wiki/`
- สร้าง `index.md` และ `log.md` จากเทมเพลตข้อ 4

**สเต็ป 2 — วางกติกา**
- เพิ่มบล็อก "Wiki schema" (ข้อ 5) ลงใน `CLAUDE.md`/`AGENTS.md` ของโปรเจค
- ปรับ path ให้ตรงโปรเจค

**สเต็ป 3 — Distill ของที่มี**
- เลือกไฟล์ดิบที่ใหญ่/สำคัญ 3-5 ไฟล์
- กลั่นแต่ละไฟล์เป็น 1 หน้า distilled (Insight/Decision/Next-action + ลิงก์กลับ raw)
- ลงบันทึกทุกหน้าใน index จัดตาม PARA

**สเต็ป 4 — เดินระบบ**
- ทดสอบถามคำถามจริง → ดูว่า AI อ่าน index ก่อนแล้ว route ถูกไหม
- ปรับ index ให้คมขึ้นถ้ายัง route ผิด

**สเต็ป 5 — automate (เมื่อพร้อม)**
- เพิ่ม skill `/ingest`, `/lint`
- เพิ่ม subagent/workflow ตามงานซ้ำของโปรเจค (multi-agent)

**สเต็ป 6 — บำรุงรักษา**
- lint เป็นรอบ, ย้าย Project ที่จบไป Archive, อัปเดต log ทุกการตัดสินใจสำคัญ
