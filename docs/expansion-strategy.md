# LLOOP · กลยุทธ์ขยายเฟสถัดไป — 5 โมเดล + แผนเฟส

> โจทย์: ขยายให้มากกว่า "เช่าชุด" โดยสร้างคูเมือง (moat) ที่เจ้าอื่นตามลอกไม่ได้
> หลักคิด: หน้าเว็บ/ราคา/สต็อก ลอกได้ใน 3 เดือน — สิ่งที่ลอกไม่ได้มี 4 อย่างคือ
> **เครือข่าย (network effect) · ข้อมูลสะสม (data) · ต้นทุนการย้ายค่าย (switching cost) · การผูกซัพพลาย (supply lock-in)**

## โมเดล C — Trust Score "เช่าไม่ต้องวางมัดจำ"
*คูเมือง: ข้อมูลความเชื่อใจสะสม (data + switching cost)*

### กลไก
ทุกการเช่า-คืน-สภาพชุดตอนคืน (QC) ของลูกค้าแต่ละคน ผูกกับตัวตน LINE + KYC กลายเป็นคะแนนความเชื่อใจ ระดับสูงขึ้น → มัดจำลดจนเป็นศูนย์, เข้าถึงชุดราคาสูงขึ้น, จองคิวก่อน, คืนช้าได้ผ่อนปรน

### ทำไมเจ้าอื่นแข่งไม่ได้
- เจ้าใหม่ไม่มีประวัติลูกค้า จึง**จำเป็นเชิงโครงสร้าง**ต้องเก็บมัดจำสูงเพื่อกันความเสี่ยง → UX แพ้เราตั้งแต่ต้น ไม่ใช่เพราะทำไม่เก่ง
- ลูกค้าย้ายค่าย = score เป็นศูนย์ = กลับไปวางมัดจำ → switching cost เกิดเองโดยไม่ต้องบังคับ
- ยิ่งเปิดนาน ช่องว่างยิ่งถ่าง (คูเมืองแบบ compounding)

### ทุนที่มีแล้ว (~70%)
ตัวตน LINE + `submit_kyc` + ประวัติเช่า/คืน + QC photo ตอนรับคืน + `customer_touchpoints` — ข้อมูลดิบครบ ขาดแค่ชั้นคำนวณและชั้นแสดงผล

### ต้องสร้างเพิ่ม
1. สูตรคะแนน (RPC เช่น `trust_score_get`) — เริ่มจากกติกาง่าย: คืนตรงเวลา +, สภาพชุดผ่าน QC +, เคลม/พิพาท −
2. ตารางสิทธิ์ต่อระดับ (tier) ผูกเข้ากับ `quote_rental` (ลด/ยกเว้นมัดจำอัตโนมัติ)
3. หน้าแสดงระดับใน LINE ("สมุดพกของฉัน") — ให้ลูกค้า *เห็น* สิ่งที่ตัวเองสะสม จึงจะรู้สึกเสียดายถ้าย้าย

### เศรษฐศาสตร์
- ไม่เพิ่มต้นทุนสต็อก แต่เพิ่ม conversion (มัดจำคือ friction อันดับต้นของการเช่าชุดแพง)
- ความเสี่ยงชุดหาย/พังเพิ่มขึ้นเฉพาะกลุ่ม tier สูง ซึ่งเป็นกลุ่มที่ข้อมูลบอกว่าเสี่ยงต่ำสุดอยู่แล้ว → เสี่ยงที่ "เลือกแล้ว" ไม่ใช่เสี่ยงหว่าน

### ความเสี่ยง / เงื่อนไขต้องเป็นจริง
- ต้องมี KYC จริงจังก่อนปลดมัดจำ (มีแล้ว) และเพดานมูลค่าชุดต่อ tier
- Cold start: ลูกค้าเก่าควรได้ score ย้อนหลังจากประวัติเดิมทันที — เปิดตัวแล้วมีคนได้สิทธิ์วันแรกเลย ไม่ใช่เริ่มนับศูนย์ทุกคน
- อย่าทำสูตรซับซ้อนเกิน: ลูกค้าต้องอธิบายได้ในประโยคเดียวว่า "ทำไมฉันได้/เสียคะแนน"

### KPI
% ออเดอร์ที่ไม่ต้องวางมัดจำ · conversion ของชุดราคาสูง · repeat rate ของ tier 2+ · อัตราเคลมต่อ tier

## โมเดล B — Garment Passport "สมุดพกเสื้อผ้า"
*คูเมือง: มาตรฐาน + ข้อมูลติดตัวชุด (switching cost ฝังในตัวสินค้า)*

### กลไก
ชุดทุกตัวที่ผ่านมือ LLOOP มีประวัติสาธารณะ: ซักกี่ครั้ง ซ่อมอะไร ตำหนิตรงไหน ถูกใส่กี่งาน — แตะ NFC หรือสแกนแล้วเห็นทันที เหมือน "รถมีเล่ม" มูลค่าขายต่อ/ปล่อยเช่าต่อของชุดจึง**ขึ้นกับการมีประวัติในระบบเรา**

### ทำไมเจ้าอื่นแข่งไม่ได้
- ชุดที่ออกจากระบบ = ประวัติขาด = มูลค่าตก → เจ้าของชุด (ทั้งเราและผู้ฝาก) ไม่อยากเอาชุดไปหมุนที่อื่น
- เป็นคูเมืองที่แข็งขึ้นตามเวลา: passport อายุ 3 ปีลอกไม่ได้ด้วยเงิน ต้องใช้เวลา 3 ปีเท่านั้น
- ถ้าทำสำเร็จจะกลายเป็น *มาตรฐานตลาด* — ผู้ซื้อมือสองเริ่มถามหา "มีประวัติ LLOOP ไหม" เหมือนถามหาเล่มรถ

### ทุนที่มีแล้ว (~80% ฝั่ง ops, ~30% ฝั่งสาธารณะ)
`tag_register/scan/lookup/missing` + care-label.html + nfc.html + ประวัติซัก/ซ่อม/QC ครบทุกจุดสัมผัส — ขาดแค่ "หน้าสมุดพกฉบับสาธารณะ" ที่สวยและอ่านรู้เรื่องสำหรับคนนอก

### ต้องสร้างเพิ่ม
1. หน้า passport สาธารณะต่อชุด (จาก `tag_lookup`) — timeline ประวัติ + รูป + จำนวนรอบใส่
2. ใบรับรองสภาพตอนขายต่อ (ผูกกับ `request_to_buy` ที่มีแล้ว) — "มือสองมีสมุดพก" ตั้งราคาสูงกว่ามือสองทั่วไปได้
3. นโยบายว่าข้อมูลไหนเปิด/ปิด (ตำหนิเปิดหมด = จุดขายความโปร่งใส ซึ่งสอดคล้องกับฟีเจอร์ flaw-transparent rentals ที่เพิ่ง merge)

### เศรษฐศาสตร์
- ต้นทุนหลักคือป้าย NFC ต่อชุด (จ่ายครั้งเดียว อยู่ทั้งอายุชุด) — ระบบติดป้ายมีอยู่แล้ว มีแต่ marginal cost ของหน้าเว็บ
- รายได้ทางตรง: ราคาขายต่อสูงขึ้น + ค่าธรรมเนียมออกใบรับรอง / ทางอ้อม: เพิ่มความกล้าฝากของโมเดล A มหาศาล

### ความเสี่ยง
- ถ้าสต็อกหมุนน้อย ประวัติจะบาง — passport มีพลังเมื่อชุดมี "เรื่องราว" แล้วเท่านั้น จึงควรเริ่มจากชุดยอดนิยม
- ความโปร่งใสมีคม: ชุดที่ประวัติซ่อมเยอะจะขายยากขึ้น → ต้องออกแบบการเล่าให้เป็น "ดูแลดี" ไม่ใช่ "พังบ่อย"

### KPI
% สต็อกที่มี passport สาธารณะ · ยอดสแกน/แตะต่อเดือน · ส่วนต่างราคาขายต่อ ชุดมี passport vs ไม่มี

## โมเดล A — "ตู้เสื้อผ้าแห่งชาติ" ตลาดฝากเช่าสองฝั่ง
*คูเมือง: network effect (winner-take-most)*

### กลไก
ฝั่งอุปทาน: คนมีชุดดี ๆ ใส่ปีละครั้ง เอามาฝาก LLOOP ปล่อยเช่า แบ่งรายได้ / ฝั่งอุปสงค์: คนเช่าได้ชุดหลากหลายขึ้นเรื่อย ๆ — ยิ่งตู้เข้าเยอะ ชุดยิ่งหลากหลาย คนเช่ายิ่งมา คนฝากยิ่งอยากฝาก หมุนเสริมกันเอง

### ทำไมเจ้าอื่นแข่งไม่ได้
- เจ้าที่มาทีหลังเริ่มจากตู้ว่าง ต่อให้ทุนหนากว่าก็ซื้อ network effect ไม่ได้
- จุดที่คู่แข่ง P2P เปล่า ๆ ตาย: **ความกล้าฝากชุดแพง** — LLOOP มี trust layer จริง (QC photo, NFC, ซัก-ซ่อมมาตรฐานเดียวทั้งระบบ, สัญญา, payout) ที่แพลตฟอร์มจับคู่เฉย ๆ ไม่มี
- เสริมกับ B: ชุดฝากได้ passport → มูลค่าเพิ่ม → ยิ่งไม่อยากถอนออก / เสริมกับ C: คนเช่ามี trust score → เจ้าของชุดกล้าให้เช่า

### ทุนที่มีแล้ว (~60%)
`seller_submit` + KYC + `ops_partner_payouts` (จ่ายส่วนแบ่งได้แล้ว) + intake/QC/tag ทั้งลูป + contracts — โครงถูกวางไว้แล้วสำหรับ "ขาย" (Closet Cash) ต้องต่อท่อให้เป็น "ฝากเช่า"

### ต้องสร้างเพิ่ม
1. โฟลว์ฝากเช่า: ประเมินค่าเช่า/รอบคุ้มทุน + สัญญาฝาก (แก้จาก contracts เดิม) + dashboard เจ้าของตู้ (ชุดฉันถูกเช่ากี่ครั้ง ได้เงินเท่าไร — หน้าจอเดียวที่ทำให้คนไปเล่าต่อ)
2. เกณฑ์คัดชุดเข้า (แบรนด์/สภาพ/แนวที่ waitlist+wishlist บอกว่าตลาดต้องการ — ใช้ `taste_trends` เลือกรับ ไม่รับเหมา)
3. นโยบายความเสียหาย: ใครรับผิดชอบเมื่อชุดฝากพัง (ประกัน/กองกลางหักจากส่วนแบ่ง)

### เศรษฐศาสตร์
- สต็อกโตโดย **ไม่ใช้ CAPEX** — จากซื้อชุดเอง (เงินจม) เป็นแบ่งรายได้ (จ่ายเมื่อเกิดรายได้)
- Margin ต่อออเดอร์ต่ำกว่าชุดของตัวเอง แต่ ROI สูงกว่ามากเพราะเงินลงทุนเป็นศูนย์ ต้นทุนจริงคือ ops (ซัก/เก็บ/พื้นที่)

### ความเสี่ยง
- ไก่กับไข่: เปิดกว้างเกินไปตอนแรก = ได้ชุดที่ไม่มีคนเช่า เปลืองพื้นที่คลัง → เริ่มแบบ curated invite-only จากลูกค้า tier สูงของโมเดล C ก่อน
- คุณภาพปนเปื้อนแบรนด์: ชุดฝากห่วยหนึ่งตัวทำร้ายความเชื่อใจทั้งร้าน → เกณฑ์คัดต้องโหดตั้งแต่วันแรก
- พื้นที่คลัง: ชุดฝากที่ไม่หมุนต้องมีนโยบายคืนเจ้าของอัตโนมัติ (เช่น ไม่ถูกเช่าใน 90 วัน)

### KPI
จำนวนตู้ที่ฝาก · % สต็อกที่เป็นชุดฝาก · รอบหมุนต่อชุดฝาก vs ชุดของเราเอง · NPS เจ้าของตู้

## โมเดล E — ความหนาแน่นเชิงพื้นที่ "ย่านต่อย่าน"
*คูเมือง: ต้นทุนต่อออเดอร์ + ความเร็ว (economies of density)*

### กลไก
ปูจุดรับ-ส่ง + ร้านซักพันธมิตรให้หนาแน่น **ทีละย่าน** (ไม่ใช่ทีละจังหวัด) จนวงจร ส่ง→ใส่→คืน→ซัก→กลับเข้าสต็อก จบภายในย่านใน 1 วัน → ชุดหนึ่งตัวหมุนได้ถี่ขึ้น ค่าส่งต่อออเดอร์ต่ำลง เช่าด่วน "พรุ่งนี้ใส่" กลายเป็นไปได้

### ทำไมเจ้าอื่นแข่งไม่ได้
- คู่แข่งที่ส่งไปรษณีย์ข้ามจังหวัด: ชุดจมอยู่ในกล่อง 4–6 วันต่อรอบ ในเวลาเท่ากันเราหมุนได้ 2–3 รอบ — ราคาเราถูกกว่าได้โดยกำไรต่อชุดสูงกว่า
- จะสู้ต้องลงทุนเครือข่ายทั้งย่านก่อนถึงจะเห็นผล ซึ่งไม่มีใครกล้าจ่ายเพื่อ "ไล่ตาม"
- ร้านซัก/จุดรับที่เซ็นกับเราแล้ว มีเหตุผลน้อยมากที่จะรับเจ้าที่สองซึ่งมีวอลุ่มน้อยกว่า

### ทุนที่มีแล้ว (~50%)
`branch_list` + `pickup_upsert/list` (โครงเฟส 2 วางแล้ว) + laundry-shops portal + repair vendors — ขาดแค่การ *เลือกย่านแรกให้ถูก* กับ SLA จริง

### ต้องสร้างเพิ่ม
1. เลือกย่านนำร่องจากข้อมูลจริง: heat map ที่อยู่จัดส่งจากประวัติออเดอร์ (มี Google Maps key อยู่แล้ว)
2. SLA ต่อย่าน: จุดรับภายใน X นาทีจาก BTS/ที่พัก, ซักคืนสต็อกภายใน 24 ชม.
3. หน้า "เช่าด่วนพรุ่งนี้ใส่" เฉพาะย่านที่รองรับ — ฟีเจอร์ที่คู่แข่งส่งไปรษณีย์เลียนแบบไม่ได้เลย

### เศรษฐศาสตร์
- นี่คือโมเดลเดียวใน 5 ตัวที่ **ใช้เงินลงทุนจริง** (ดีลจุดรับ, วอลุ่มขั้นต่ำร้านซัก) → ต้องทำทีละย่านและวัดก่อนขยาย
- ผลตอบแทนอยู่ที่ asset turnover: ชุดเดิม รายได้ x2–3 เพราะรอบหมุนถี่ขึ้น

### ความเสี่ยง
- ขยายเร็วเกิน = เผาเงิน — วินัยคือ "ย่านที่สองต่อเมื่อย่านแรกกำไร"
- คุณภาพร้านซักพันธมิตรไม่สม่ำเสมอ → มาตรฐาน + QC ตอนรับกลับ (มีระบบอยู่แล้ว) ต้องเข้มจริง

### KPI
รอบหมุนต่อชุดต่อเดือนในย่าน vs นอกย่าน · ต้นทุนส่งต่อออเดอร์ · % ออเดอร์เช่าด่วน · กำไรต่อย่าน

## โมเดล D — "เปิดตัวคอลเลกชันบน LLOOP ก่อนใคร"
*คูเมือง: ผูกซัพพลาย exclusive (แบบ Netflix originals)*

### กลไก
ดีลดีไซเนอร์/แบรนด์ไทย: คอลเลกชันใหม่ปล่อย **เช่าบน LLOOP ก่อนวางขายจริง** แบ่งรายได้ต่อรอบเช่า — แบรนด์ได้ 3 อย่าง: รายได้ก่อนผลิตล็อตใหญ่, ข้อมูลจริงว่าแบบไหน/ไซซ์ไหนคนชอบ (จาก taste_trends + wishlist + รีวิว), การตลาดฟรีจากคนใส่จริงถ่ายลง social (creator credits + UGC มีระบบรองรับแล้ว)

### ทำไมเจ้าอื่นแข่งไม่ได้
- ของ exclusive คือของที่ *ไม่มีที่อื่น* — คู่แข่งลดราคาสู้ได้ แต่เอาชุดตัวนี้ไปให้ลูกค้าไม่ได้
- ยิ่งฐานผู้เช่า + ข้อมูลรสนิยมใหญ่ (ผลจาก A+C) แบรนด์ยิ่งไม่มีเหตุผลไปลงเจ้าอื่น → moat นี้ *ซื้อด้วยผลของ moat อื่น*

### ทุนที่มีแล้ว (~40%)
`taste_trends`, `mkt_overview`, `submit_garment_request` (สัญญาณดีมานด์), UGC/creator/looks pipeline, contracts + partner payouts (โครงแบ่งรายได้มีแล้ว)

### ต้องสร้างเพิ่ม
1. Pitch deck ตัวเลขจริงให้แบรนด์: ยอดเช่า, demographic, ตัวอย่าง insight ("เดรสเปิดไหล่โทนเอิร์ธถูก wishlist มากสุดในไตรมาสนี้")
2. หน้าคอลเลกชัน + waitlist countdown (waitlist มีแล้ว)
3. Dashboard รายงานผลให้แบรนด์ (จำนวนรอบเช่า, รีวิว, รูป UGC) — นี่แหละของที่แบรนด์อยากได้จริง

### เศรษฐศาสตร์
- ไม่ซื้อสต็อก (แบ่งรายได้) แต่ต้นทุนคือ **การขาย B2B** — ใช้เวลาผู้ก่อตั้งเยอะ
- อย่าเริ่มก่อนมีตัวเลขน่าอวด: ดีลแรกจะง่ายขึ้น 10 เท่าเมื่อโชว์ได้ว่า "ชุดแนวคุณถูกเช่า X ครั้ง/เดือนบนแพลตฟอร์มเรา"

### ความเสี่ยง
- ทำเร็วไป = โดนปฏิเสธและเสียเครดิต → เป็นโมเดลของเฟส 3 โดยธรรมชาติ
- เริ่มจากดีไซเนอร์อิสระ/แบรนด์เล็กที่อยากได้ข้อมูล ก่อนไปแบรนด์ใหญ่

### KPI
จำนวนดีล exclusive · รอบเช่าต่อชุด exclusive vs ปกติ · ลูกค้าใหม่ที่เข้ามาเพราะคอลเลกชัน

## ภาพรวม: โมเดลไหนเสริมกันอย่างไร

```
C (trust score)  ──ทำให้คนเช่าน่าเชื่อถือ──►  A (เจ้าของตู้กล้าฝาก)
B (passport)     ──ทำให้ชุดฝากมีมูลค่า/ถอนไม่ออก──►  A (ตู้ไม่ไหลออก)
A (ตู้เยอะ)      ──ทำให้ selection ใหญ่สุด──►  D (แบรนด์อยากลง)
C+ข้อมูลรสนิยม   ──ทำให้มี insight ขาย──►  D (ข้อเสนอที่แบรนด์ปฏิเสธยาก)
E (ความหนาแน่น)  ──ทำให้หมุนถี่ ต้นทุนต่ำ──►  ทุกโมเดลกำไรขึ้น
```

คู่แข่งที่จะล้ม LLOOP ต้องเจาะทั้ง 4 ชั้นพร้อมกัน: มีตู้เท่าเรา (A) + มีประวัติชุดเท่าเรา (B) + มีประวัติลูกค้าเท่าเรา (C) + แย่งดีล exclusive (D) — ซึ่งชั้น B และ C ซื้อด้วยเงินไม่ได้ ต้องใช้เวลาเท่านั้น

## แผนเฟส

### เฟส 1 (เดือน 0–6): ปักเสาเข็มข้อมูล — C เต็มตัว + B ฉบับสาธารณะ
*ธีม: ของที่แข็งขึ้นตามเวลา ต้องเริ่มก่อนเพื่อน เพราะซื้อทีหลังไม่ได้*

> สถานะ ก.ค. 2026: สวิตช์เปิด-ปิดทั้ง 4 ตัว (trust_show / trust_pricing / passport_public / consign_open) อยู่ในหน้า owner (settings.html) แล้ว + trust score v1 ติดตั้งตาม `sql/2026-07-expansion-flags-trust.sql` + หน้าลูกค้า "สมุดพกของฉัน" (trust.html) พร้อมแล้ว รอเปิดสวิตช์ — ส่วนเก็บข้อมูลทำงานตลอดไม่มีสวิตช์ คะแนนสะสมเงียบ ๆ ตั้งแต่วันติดตั้ง

- [ ] Trust score v1: สูตรง่าย 3 ปัจจัย (ตรงเวลา/สภาพคืน/พิพาท) + คำนวณย้อนหลังให้ลูกค้าเก่าทันที
- [ ] Tier + สิทธิ์: ผูก `quote_rental` ลด/ยกเว้นมัดจำอัตโนมัติ + เพดานมูลค่าชุดต่อ tier
- [ ] หน้า "สมุดพกของฉัน" ใน LINE (score, tier, สิทธิ์ถัดไป)
- [ ] Garment passport สาธารณะ: หน้า timeline ต่อชุดจาก `tag_lookup` เริ่มจากชุด top-50 ที่หมุนบ่อยสุด
- [ ] เก็บ heat map ที่อยู่จัดส่ง (เตรียมข้อมูลเลือกย่านให้เฟส 2 — เก็บวันนี้ ใช้พรุ่งนี้)
- เกณฑ์ผ่านเฟส: ≥30% ออเดอร์ repeat ไม่วางมัดจำ · เคลม tier สูงไม่เกิน baseline · ชุดมี passport ครบ top-50

### เฟส 2 (เดือน 6–18): เปิดสองเครื่องยนต์โต — A (curated) + E (ย่านแรก)
*ธีม: ใช้ความเชื่อใจจากเฟส 1 มาแลกเป็นซัพพลายและความเร็ว*

- [ ] ฝากเช่า invite-only: ชวนลูกค้า tier สูงสุด 20–30 คนแรกฝากตู้ (คนที่ระบบรู้จักดีที่สุด = เสี่ยงต่ำสุด + เป็นแฟนอยู่แล้ว)
- [ ] Dashboard เจ้าของตู้ + payout อัตโนมัติ (ต่อยอด `ops_partner_payouts`)
- [ ] เกณฑ์คัดชุดจาก `taste_trends`/wishlist — รับเฉพาะแนวที่ดีมานด์ยืนยันแล้ว + นโยบายคืนชุดไม่หมุนใน 90 วัน
- [ ] ย่านนำร่อง 1 ย่าน (เลือกจาก heat map เฟส 1): จุดรับ-ส่ง + ร้านซัก SLA 24 ชม. + หน้า "เช่าด่วนพรุ่งนี้ใส่"
- [ ] ขยายฝากเช่าเป็น open-with-criteria เมื่อ NPS เจ้าของตู้ ≥ 8
- เกณฑ์ผ่านเฟส: ชุดฝาก ≥25% ของสต็อก · รอบหมุนในย่านนำร่อง ≥2 เท่านอกย่าน · ย่านแรกกำไร

### เฟส 3 (เดือน 18–36): เก็บเกี่ยวคูเมือง — D + ย่านที่ 2–3 (+ ทางเลือก SaaS)
*ธีม: ขายผลของ moat ที่สะสมมา ให้ฝั่ง B2B*

- [ ] Pitch แบรนด์/ดีไซเนอร์อิสระ 3–5 ราย ด้วยตัวเลขจริงจากเฟส 1–2 → คอลเลกชัน exclusive แรก + dashboard รายงานผลให้แบรนด์
- [ ] ขยาย E ไปย่านที่ 2–3 ด้วย playbook ย่านแรก (ขยายต่อเมื่อย่านก่อนหน้ากำไรเท่านั้น)
- [ ] Passport เป็นมาตรฐานขายต่อ: ใบรับรองสภาพ + ตลาดมือสอง "มีสมุดพก" (ต่อยอด `request_to_buy`)
- [ ] ทางเลือก: เปิดหลังบ้านเป็น SaaS ให้ร้านเช่าชุดรายเล็ก — ทำต่อเมื่อระบบนิ่งจากการใช้เองแล้ว และร้านที่ใช้ระบบเรากลายเป็นจุดรับ-ส่ง/ซัพพลายในเครือข่ายเราไปในตัว
- เกณฑ์ผ่านเฟส: ≥1 คอลเลกชัน exclusive ที่ sold-out คิวเช่า · ราคาขายต่อชุดมี passport สูงกว่าตลาด ≥20%

### สิ่งที่ตั้งใจ *ไม่ทำ* ในทุกเฟส
- ไม่เปิดฝากเช่าแบบใครก็ฝากได้ตั้งแต่วันแรก (ปนเปื้อนคุณภาพ = ทำลายแบรนด์)
- ไม่ขยายย่านที่สองก่อนย่านแรกกำไร (เผาเงิน)
- ไม่ pitch แบรนด์ใหญ่ก่อนมีตัวเลข (เสียเครดิตแล้วกลับไปขอใหม่ยาก)
- ไม่ทำ SaaS ก่อนระบบนิ่ง (ขายความนิ่ง ไม่ใช่ขายฟีเจอร์)
